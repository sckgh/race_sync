# 07 — Race-Management Audio Bridge

One Race Control voice should reach everyone — real drivers and virtual drivers alike. The
event already runs a sanctioned **one-way** race-management comms stack; RaceSync **bridges**
it to the virtual field rather than building or replacing it.

## 7.1 What already exists (and why we reuse it)

From the Special Regulations (#02 §2.4):

- **Race Receivers** (one-way radios) carry Race Control safety messages, **Safety Car
  deployment**, emergency-vehicle alerts, etc. to real drivers (Art. 10.1–10.2).
- The official **Zello channel `MRA-RMC`** carries the same content — **all Race Receiver
  transmissions are mirrored onto `MRA-RMC`** (Art. 10.5) — plus team/pit messages.
- The channel is **one-way**: Race Control / Organiser → participants; **no one else may
  transmit** without authorisation (Art. 10.7). Teams may relay to cars (Art. 10.9).

`MRA-RMC` is therefore already the **authorised, one-way superset** of everything broadcast
to the real field. Bridging it gives virtual drivers exactly what real drivers hear, from a
single source of truth, with no new transmit path to misuse. This is why the chosen approach
is **"bridge existing Zello `MRA-RMC`."**

## 7.2 Design

```
  Race Control voice ──▶ Race Receiver RF  ──▶ real drivers
            │
            └──▶ Zello "MRA-RMC" (1-way) ──▶ teams/pit/drivers (existing)
                          │
                          ▼
                 ┌──────────────────┐
                 │  Audio Bridge C5  │  (subscribes to MRA-RMC as a listener)
                 │  • capture audio  │
                 │  • buffer/jitter  │
                 │  • re-broadcast   │
                 └────────┬─────────┘
                          ▼
                 virtual drivers' audio
              (in-sim voice / app / Zello mirror)
```

- **Ingress:** the bridge joins `MRA-RMC` as a **listen-only** client (it never transmits —
  respecting Art. 10.7). It captures the incoming audio stream.
- **Distribution to virtual drivers:** one or more of, decided in the spike (O-6, #10):
  1. **Re-broadcast into a virtual-drivers Zello sub-channel** the bridge controls (simplest;
     virtual drivers run Zello like everyone else).
  2. **Inject into the sim's in-game voice/audio** so it comes through the same headset as
     engine/spotter audio (most immersive; platform-dependent — validate in #05/#07 spike).
  3. **A lightweight RaceSync audio client** (web/app) virtual drivers run alongside the sim.
- **Direction stays one-way.** Virtual drivers **receive only**. There is no virtual→control
  audio path (matches regs and the project non-goals, #01 §1.4).

## 7.3 State-coupled audio cues (belt and braces)

Audio is the human-facing twin of the state machine (#06). Independently of the spoken
`MRA-RMC` content, RaceSync SHOULD give virtual drivers **unambiguous machine cues** for
state, so a missed or noisy transmission can't leave them unaware:

| Event (#06) | Virtual-driver cue |
|-------------|--------------------|
| GREEN (start/restart) | Audio + on-screen "GREEN" |
| NEUTRALISED → CODE 60 | Distinct tone + persistent on-screen "CODE 60" banner |
| Back to GREEN | "GREEN" cue; banner clears |
| CHEQUERED (timed finish) | "CHEQUERED FLAG" cue |

These are generated by RaceSync from the state engine, **in addition to** (not instead of)
the relayed `MRA-RMC` voice. The relayed voice remains the authoritative human message.

## 7.4 Quality, latency, sync

- **Latency:** race-management audio is informational, not split-second, so a modest delay
  is acceptable — but it should be **bounded and roughly consistent** with what real drivers
  hear, and the **CODE 60 machine cue (7.3) should not lag the state transition** (that cue
  comes from the state engine directly, not the audio path, so it can be near-instant even
  if the voice relay is a beat behind). Numeric targets in #09.
- **Jitter buffering:** the bridge buffers to smooth Zello/network jitter; intelligibility
  beats latency for voice.
- **Resilience:** if the `MRA-RMC` ingress drops, the bridge alarms the operator (C7) and
  the **state machine cues (7.3) continue regardless**, so virtual drivers still get GREEN/
  CODE 60/CHEQUERED even during an audio outage.
- **Audio-only fidelity:** the bridge handles voice; it does not attempt speech-to-text or
  re-interpretation in v1 (possible future captioning — O-9, #10).

## 7.5 Compliance & access

- **Listen-only** participation on `MRA-RMC` keeps RaceSync within Art. 10.7. The bridge
  must be configured so it **cannot transmit** on the official channel.
- **Access/credentials** to join `MRA-RMC` as a relay source must be arranged with the
  Organiser (**TBC-6**, #02).
- Relaying official race-control audio to additional (virtual) participants should be
  **agreed with the Organiser/Race Control** as part of the event's comms plan, since it
  extends the audience of `MRA-RMC` (sanctioning touch-point, #01 A1).

## 7.6 Requirements

- **F-07-1** The bridge MUST join `MRA-RMC` **listen-only** and MUST be incapable of
  transmitting on the official channel.
- **F-07-2** The bridge MUST relay `MRA-RMC` audio to virtual drivers via at least one
  distribution method (sub-channel, in-sim audio, or RaceSync client), one-way only.
- **F-07-3** The system MUST emit independent **machine cues** for GREEN / CODE 60 / GREEN /
  CHEQUERED to virtual drivers, sourced from the state engine, not dependent on the voice
  relay.
- **F-07-4** The bridge MUST buffer for jitter and MUST alarm the operator on ingress loss,
  while state cues continue.
- **F-07-5** Audio latency and the CODE 60 cue timing MUST meet #09 targets.
- **NF-07-1** Relaying `MRA-RMC` to virtual participants MUST be covered by the event comms
  plan / Organiser approval (TBC-6).
